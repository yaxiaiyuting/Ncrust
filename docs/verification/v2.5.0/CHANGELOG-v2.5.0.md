# v2.5.0-gpl 更新说明

> **目标 tag**：`v2.5.0-gpl`　**versionCode**：41（三源交叉校验见「发布校验」一节）
> **探针**：`docs/verification/v2.5.0/PROBE-SUMMARY.md` + 五份 `probe-*.md`
> **证据**：`docs/verification/v2.5.0/EVIDENCE.md`

## 一句话

这一版做三件事：**给界面建立一套统一的圆角与动效规范**、**给专辑封面加圆角与描边**、
**修好「添加到下一首播放」**（它此前已存在，但在三个边界上是坏的）。

---

## 一、给用户看的（按你会感知到的顺序）

### 1. 新增：「添加到下一首播放」

**在哪用**

- **任意歌曲长按菜单**（首页 / 歌单 / 专辑 / 歌手 / 收藏 / 搜索 / 本地歌单 —— 全应用同一个菜单）；
- **单曲详情页**每一行的版本，播放键**左侧**多了一个按钮。

**它和已有的两个动作有什么区别**（这三个经常被混为一谈）

| 动作 | 行为 |
|---|---|
| **播放** | 立刻打断当前播放，放这一首 |
| **插播**（已有） | 立刻把这一首插到队首并播放 |
| **添加到下一首播放**（新） | **完全不打断**当前播放，只把它排到当前歌之后 |

**会出现一行提示**告诉你这次到底发生了什么：已添加 / 已移到下一首 / 已在下一首 /
这首歌正在播放 / 队列为空已直接播放。

**修好的三个真实问题**

1. **队列为空时点了没反应** —— 现在会直接开始播放（这是"什么都没有在播"时最自然的预期）；
2. **随机播放模式下这个功能是失效的** —— 以前它会重新洗一次牌，于是"下一首"仍然是原来那首随机歌，
   你加的歌不知道跑到哪里去了。现在它会**真的**排在下一首；
3. **有时会「显示加了 A、耳朵里却是 B」** —— 这是最隐蔽的一个：播放器已经悄悄预载好了"原来的下一首"，
   加歌之后它**仍然会播那一首**。现在加完歌会立刻把预载换掉。
   （这一类问题在这个应用里叫「串台」，v1.5.2 修过一次，这次是新入口又触发了一次。）

**一条明确的行为决定**：如果这首歌**已经在下一首**的位置上，再点一次**不会**重复添加，
只会提示「已在下一首」。同一首歌在队列里最多只会有一份。

**单曲循环模式下**：歌会正常排进队列，但因为单曲循环的语义就是"一直重播这一首"，
它不会立刻被预载 —— 退出单曲循环后它自然就是下一首。**不会**为了这个功能偷偷帮你换播放模式。

### 2. 专辑封面有了圆角和描边

大封面（播放页、详情页的整屏宽封面）**16dp 圆角**，列表和菜单里的小封面（56 / 72 / 112dp）
**8dp 圆角**，都带一圈 1dp 的弱描边，把封面和背景分开。

按尺寸分两档是**有意**的：任务要求是「大/小封面视觉协调」，而 16dp 圆角放在 56dp 的缩略图上
会吃掉将近一半的边长，看起来像个团块。

**通知栏的封面没有动** —— 那是系统自己的界面，应用去裁它的圆角只会和系统打架。

### 3. 统一的圆角与动效

- 列表行 8dp、卡片 12dp、封面 16dp、弹窗 28dp、按钮/搜索框/音源标签药丸形；
- 所有**新增**的动效走同一套规格；
- 列表开头的内容出现时**淡入 + 轻微上滑**（只对前 12 项，快速甩动长列表时一个动画都不会起 ——
  这是给低端机留的余量）；
- 歌曲行、卡片、单曲页的按钮按下去有 1.05x 的回弹。

### 4. 播放器展开/收起改成了弹簧

比原来的固定时长曲线更跟手。**并且刻意选了不过冲的那一档** —— 原因见下面「工程说明」，
简单说：那个动画的进度值同时是"哪些部件要挂载"的开关，让它回弹会导致画面抖动。

## 二、工程说明（给下一个改这份代码的人）

### 本版修正了三处任务书的前提（**这一节最重要**）

按铁律 2「探针先行，不直接采信任务书中的初步判断」，实测下来任务书有三处前提不成立。
**结论不是"因此什么都不做"**，而是把依据换成一手的、把不成立的部分如实标出来。

| 任务书原文 | 实测 | 本版处置 |
|---|---|---|
| 「参考 **SPlayer-Next**」的取色与圆角规范 | `SPlayer-Dev/SPlayer-Next` 是 **Electron + Vue 3 + Rust 的桌面端**应用。浅克隆后 `find` 查 `*.gradle*` / `AndroidManifest.xml` / `*.kt` / `pubspec.yaml` **全部为空**。「50×50 采样」「`Score` 评分」两条**只存在于该项目 `color.ts` 的一句 JSDoc 注释**里 —— 真实常量是 `COVER_SAMPLE_SIZE = 64`，且该文件**从未 `import Score`** | 圆角**取值照收**（它另有 Google 一手出处：androidx `ShapeTokens.kt` 与 MDC `Shape.md` **逐值一致**），但**不引用 SPlayer-Next 作为依据** |
| 「Material 3 Expressive 弹簧动效**四档**」 | 官方表述是「**三种速度** × **两种类型** = **六个弹簧**」（MDC `Motion.md` 原文，androidx 里正好 6 个 token）。而且官方**没有任何** spring→tween 的对应值（`MotionScheme` 的 12 个 spec 全是 `spring(...)`） | `AppMotion` 按「官方空间三档 + 官方 effects 三档 + 本项目既有 tween 词汇」组织，每类出处写进代码注释 |
| 「使用 `player.addMediaItem(index, mediaItem)`」 | 本工程的队列在**应用层**（`MainScreen.playbackQueue`），ExoPlayer 的播放列表**不是队列**，只承载 `[当前项]` 或 `[当前项, 待播项]`。真按任务书写法会往列表里塞第三项，**直接破坏 v1.5.2 立下的待播槽位不变量** | 改为「改应用队列 + 重新同步待播槽位」 |

> 附带一句：探针还发现 `m3.material.io` 的页面**全部抓不到正文**（每页都是约 62 KB 的
> 客户端渲染外壳，Wayback 快照同样）。所以本版所有 shape/motion 结论的出处是
> **Google 的代码仓库**，不是 m3.material.io。这一点在 `probe-splayer-ref.md` §9 有完整清单。

### 两处动效是「受约束的落地」，不是照抄

1. **播放器展开/收起用临界阻尼弹簧（不过冲）**。`progress` 同时是命中测试的开关：
   `< 0.01f` 卸载展开态子树、`> 0.99f` 卡片吞掉所有事件。官方三档 spatial 的
   `dampingRatio` 都 < 1（会过冲），会让 `progress` 反复跨越这两个阈值
   ⇒ 子树挂载抖动 + 命中区闪烁。所以固定 `dampingRatio = 1.0`，
   并由 `AppMotionSpecTest` 断言钉死，防止下一个人"顺手调成 0.6 更活泼"。
2. **列表入场动效必须有界**：只对下标 < 12 的项播放，判定是纯函数 + 单测。
   快速甩动长列表时一个动画都不会起（铁律 15：动效不得影响播放性能）。

### 三条**有意不做**（不是遗漏）

| 不做 | 理由 |
|---|---|
| **页面切换转场**（任务书 §3.3 要求） | `ui/navigation/NavGraph.kt` 把四个转场**显式**设成 `None`，并且注释写明这是**用户决策**、理由是「转场期间新旧两页同帧渲染，每帧全屏合成，低端机上是切换动作的主要掉帧源」。任务书没有给出任何新证据说明"现在不掉了"，而目标是 Android 7.0 / 3GB RAM。**交回产品决策**，代码里留了 `AppMotion.PAGE_TRANSITION_MS` 与取证要求 |
| 把 41 处存量手写 `tween` 批量改走 `AppMotion` | 逐处判断"空间类还是效果类"要读 41 处上下文，改错会让手感变化且**无法归因**；其中 `PlayerCard.kt` / `NcrustLyricsPanel.kt` 被 `AGENTS.md` 标注为承重、禁止批量重构 |
| 改 Kanesumi 库（用户裁定） | 会让发布产物依赖另一个仓库的未发布提交，破坏「`git clone` 即可复现发布产物」（v1.5.0 把 `MetroLyricsPanel` 搬进本仓库正是同一条理由）。**代价**：库内部的弹窗/按钮背板保持直角，已列入遗留清单 |

### 三条**把约定变成会变红的测试**的守卫

约定写在文档里会被绕过（41 处手写 `tween` 就是证据），写进测试才会变红：

| 测试 | 钉住的事实 |
|---|---|
| `AppShapesSingleSourceTest` | 圆角构造器**只能**出现在 `AppShapes.kt`（扫全源码树，并自检"确实扫到了文件"以防空扫描恒绿） |
| `AppMotionSpecTest` | ① 官方六弹簧逐值；② **播放器转场不得过冲**；③ `spring(` 只能来自 `AppMotion` |
| `ListItemAppearTest` | 入场动效**必须有界**（阈值在 1..64，边界是半开区间） |
| `QueueInsertTest` | 铁律 16 的四条边界 + 乱序排列合法性（穷举 4! 全部排列） |

### ⚠️ 两条实现约束（踩过就会写出「封面不见了」）

1. **播放页封面不能在外面套 `Modifier.clip`。** 该节点布局在卡片 (0,0)，视觉位置全靠自己的
   `graphicsLayer { translationX/Y/scale }` 搬过去；clip 若排在那个 `graphicsLayer` **之前**（= 外层），
   裁切边界是**未平移的布局边界**（屏幕左上角），封面会被整块裁掉。正确顺序：**变换在外、裁切在内**。
2. **mini bar 封面是大封面同一节点被 `scale` 到 56dp 的结果**，所以圆角与描边会**等比缩放**
   （16dp → 约 2.5dp，1dp → 约 0.16dp）。这是**有意接受**的：要让它不缩放就得每帧改
   `graphicsLayer.shape` 并按 `1/scale` 反算描边宽度，那会让播放器展开/收起这条播放链路上的
   关键动画每帧重建图层属性，与铁律 15 冲突。

### i18n

新增文案全部进 `Strings` 的嵌套组 `QueueStrings`（8 条 × 8 语言）。
该组同时**吸收**了原先在主构造器上的 `actionInsertNext` / `actionAppendToQueue`
（用成员转发属性保住既有调用点），所以主构造器 **245 → 244**。
主构造器的 dex 上限是 **245**（`1 + N + ceil(N/32) + 1 <= 255`）——
**下一个要加文案的人：只剩 1 个空位，请先腾位置再加组。**
