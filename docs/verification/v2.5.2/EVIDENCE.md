## 0. 一句话

用户紧急反馈的「**歌词自动居中只把第一行居中，带翻译的多行歌词在大屏模式下很难看**」
已定位到明确的几何根因并修复：
**当前条目（原句 + 译文 + 音译）的视觉中心在 S6 大屏模式下由面板的 67.6% 移到 53.6%**
（同一台设备、同一首歌、同一测量协议，release 包与 debug 包逐像素一致）。

`clean testDebugUnitTest lint assembleDebug assembleRelease` **全绿**
（81 类 / **1100** 单测 0 失败、lint **0 Error / 0 Fatal**）。

## 1. 根因（探针结论，先说清楚"修的是哪个数"）

`NcrustLyricsPanel` 的 LazyColumn 里，**一个 item 不是「一行」**，而是：

```
Box(padding vertical 10dp) {
  Column { LyricLineBody(原句, 可能折行), [译文], [音译] }
}
```

而 v2.5.1 及以前的定位语义（`LyricsPanelScroll.leadOffsetPx`）是
「**条目顶边**落在视口 `leadFraction` 处」：

```kotlin
fun leadOffsetPx(viewportHeightPx: Int, leadFraction: Float): Int =
    if (viewportHeightPx > 0) -(viewportHeightPx * leadFraction).toInt() else 0
```

于是**行数越多、整块越往下坠**：

| 条目内容 | 高度（42/26/24sp + 20dp padding） | 大屏 232dp 视口下顶边落在正中时，整块视觉中心 |
|---|---|---|
| 只有原句 | ≈ 62dp | 63% |
| 原句 + 译文 | ≈ 88dp | 69% |
| 原句 + 译文 + 音译 | ≈ 112dp | 74% |

带翻译的歌**恰好行数最多**，所以那条反馈点名了「带有翻译的歌曲」；
竖屏面板高（约 700dp）时同样的偏移只占 5%~8%，所以反馈点名了「大屏模式」。

**真机实测（S6 / 大屏模式 / 带翻译的歌，v2.5.1 代码）**：

```
面板     : y 96..1024  h=928  中心=560
当前条目 : y 600..847  h=247  中心=724
条目中心占面板比例 = 67.6%   ← 顶边 54.3%（"第一行确实居中了"），整块中心却在 67.6%
```

## 2. 修法

**新语义：整条的中点落在 `leadFraction` 处**（`LyricsPanelScroll.blockTopPx`）：

```
top = 视口 × leadFraction − 条目高 / 2
     再夹取：top ≥ 顶部渐隐带高度（否则当前行会压在渐隐里发灰）
             top ≥ 0（条目比视口还高时退化成顶对齐）
```

三处配套改动：

| 位置 | 改动 | 为什么必须 |
|---|---|---|
| `LyricsPanelScroll` | 新增 `blockTopPx` / `blockOffsetPx` / `blockCorrectionPx` + `fadeHeightPx`（**纯函数，可单测**） | 「居中」这件事必须能被断言，不能靠肉眼 |
| `NcrustLyricsPanel` | 条目**实测高度**缓存（`snapshotFlow { layoutInfo.visibleItemsInfo }`）+ 五个滚动调用点全部改走 `placeLine` / `animateToLine` | 折行数取决于宽度与字号，**高度只能实测**；量不到时先按旧行为摆一次、同一帧用 `scrollBy` 纠正 |
| `LyricsView` | 渐隐高度公式搬进 `LyricsPanelScroll.fadeHeightPx` | 面板从本版起也要用这个数（顶边下限）。两处各写一份＝第二处真相：渐隐调窄而定位没跟着调，当前行就会被压在渐隐里发灰 |

**零重组**：条目高度缓存用普通 `HashMap`（不是 `mutableStateMapOf`）——
它只在滚动回调里读，换成 state map 会让每次布局都触发一次面板重组。

**高度未知时的行为**：`blockOffsetPx` 回落 `leadOffsetPx`，即**逐字节等于 v2.5.1**；
调用方随后用实测高度纠正。所以这条路径不会比旧版更差，只会更好。

## 3. 真机 A/B（S6 / 大屏模式 / 带翻译的歌）

协议：进入大屏模式 → **手势把歌词推走** → 等 9 秒（5 秒无触碰自动居中落地）→ `uiautomator dump` 量节点 bounds。
原始输出与公式复核：[`verification/device-verify.txt`](verification/device-verify.txt)。

| | 面板 | 当前条目 | 条目中心占面板 | 偏离面板中心 |
|---|---|---|---|---|
| **修复前**（debug 42 / v2.5.1） | y 96..1024（h=928） | y 600..847（h=247） | **67.6%** | +164px |
| **修复后**（debug 43） | 同上 | y 414..773（h=359） | **53.6%** | +34px |
| **修复后**（**release 43**，最终产物） | 同上 | y 414..773（h=359） | **53.6%** | +34px |

- **改善 130px ≈ 37dp**（占面板高度的 14 个百分点）；
- 残余 +34px **不是定位错误**：代码居中的是「条目盒」，而 uiautomator 量的是**字形框**
  （比行盒小、上下留白不对称）。复核：条目高 359+70=429px，期望顶边
  `96 + 928×0.5 − 429/2 = 345.5`，实测字形顶边 414（差 33.5px）——正是行盒与字形框之差；
- **release 与 debug 逐像素一致** ⇒ R8 不影响本修法（铁律 15 的对照）。

## 4. 单测（纯逻辑，+13 例）

`LyricsPanelScrollTest`：17 → **31** 例。新增覆盖：

| 用例 | 钉住的事实 |
|---|---|
| `回归本体——大屏三行条目：整条中点接近视口正中，而旧语义在 74 百分比处` | 本 bug 的几何本身（含"旧语义确实偏"这一半） |
| `单行条目在横屏下严格落在正中` | 新语义对单行同样是"整条居中"，不是特例 |
| `竖屏 36 百分比语义不变——只是从顶边改成整条中点` | 竖屏的目标比例没被顺手改掉 |
| `顶边永远不进顶部渐隐带` | 高条目宁可不完美居中，也不能让当前行发灰 |
| `条目比视口还高时退化成顶对齐` | 滚动容器通用行为 + 顶边不得为负 |
| `高度未知时逐字节回落 v2_5_1 的顶边语义` | 中间态不引入回归 |
| `纠正量：方向正确，且已经摆正时严格为 0` | 不做无意义滚动（无意义滚动会误触发「用户滚动了」旗子） |
| `条目放得下时整条不会越过视口底边` | 居中的副作用有界 |
| `渐隐带高度逐值与 v1_7_0 的内联公式一致` | 搬家不改数值（竖屏 100dp 一分不差） |

## 6. 未验证缺口（如实）

1. **竖屏（`leadFraction = 0.36`）的同协议 A/B 未取到**：退出大屏模式后歌词面板未挂载，
   两次尝试都拿不到面板节点。只有修复前的一次旁证测量（55.9%，同样偏下），
   以及「新语义在竖屏下把整条中点放在 36%」的单测证据。**下一轮补**。
2. **平板的 A/B 未做**：`uiautomator` 在 PLC110（ColorOS）上被系统杀掉，
   平板上未找到带翻译的目标曲目。
3. **`minTopPx`（顶边不得进渐隐带）这条夹取在真机上没有被触发过**：
   本次测量的条目高 429px 未触及该下限。它只有单测证据。
4. **动态字号（`lyrics_dynamic_font`）打开时**每行的 `fontScale` 不同，
   条目高度差异更大 —— 本修法按实测高度居中，理论上自适应，但**没有单独用动态字号的
   曲目做真机对照**。
