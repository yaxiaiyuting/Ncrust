# 探针 ⑤：**横屏歌词**的当前行为与问题根因

> v2.3.0 · 2026-09-26 真机实测。
> 设备 `0715f763f54c023a`（SM-G9209 / Android 7.0 / 1440×2560 / density 640 ⇒ 360×640dp），
> 应用 `2.2.1-gpl`（versionCode 38，与 `HEAD` 同源），大屏模式横屏（2560×1440, rotation 1）。
>
> **完整证据**：`probe-raw/landscape-device-notes.md`（主笔记）、
> `probe-raw/lyric-panel-measurements.txt`（22 个 dump 的逐节点测量总表）、
> `probe-raw/pixel-diff-report.txt`（md5 + `compare -metric AE` 的逐字节静止性证明）、
> `screenshots/`（27 张）、`logcat-landscape-baseline.txt`（12758 行）。
> **本轮未改动任何代码、未改 SharedPreferences、未卸载、未清数据**。

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 横屏歌词的定位逻辑是什么？ | 当前行滚到视口 **36%** 高处（`LyricsPanelScroll.LEAD_FRACTION = 0.36`，`animateScrollToItem`，负 offset） |
| 「有时不正」是真问题吗？ | **定位本身是精确的**：6 次独立基线（4 首歌、播放与暂停、单行与折行）**全部** `frac = 0.3599`。**不是算错**，是横屏 3 行视口下 36% 的视觉重心偏上 |
| 「手动调整后留在原地」是真问题吗？ | **复现成功，且是稳定可复现的**（见 §3） |
| 根因 | `NcrustLyricsPanel.kt` 的 5s 超时分支**只放旗子、不滚动**：`userScrolling = false; lastAutoScrolledIndex = -1`。真正的重新定位只在 `LaunchedEffect(currentIndex)` 里，而它**只在换行时**才跑 |
| 用户手动调整后状态保存在哪？ | **没有任何持久化**。`userScrolling` / `lastAutoScrolledIndex` 都是 `remember` 的进程内状态，只有「暂停跟随」这一个语义，没有「用户偏好的位置」 |
| 为什么是「留在原地」 | 5s 到点时**没有换行**（暂停 / 间奏 / 长句）⇒ `LaunchedEffect(currentIndex)` 一次都不跑 ⇒ 面板永久停在用户放手的位置 |
| 播放时为什么不明显 | 播放时每 2–3 秒换一行，跨过 5s 超时的**第一次换行**就把面板拉回去了（实测 +6.8s 的换行日志），bug 被掩盖 |
| 播放/暂停/seek 会不会重置计时？ | **都不会**（实测，见 §4）。唯一的回正触发是**换行** |

## 1. 面板几何（实测，不是估算）

| | 面板 bounds | 尺寸 | 0.36 对应的当前行 item top | 面板下方剩余 |
|---|---|---|---|---|
| **横屏** | `[1206,96][2480,1024]` | 1274 × **928px = 232.0dp** | `96 + 0.36×928 = 430px`（= 面板内 83.5dp） | ≈ 148dp（约 1.4 行） |
| **竖屏** | `[80,320][1360,1136]` | 1280 × 816px = 204.0dp | `320 + 294 = 614px` | ≈ 131dp |

横屏一屏只放得下 **3 行**（`ui-03-landscape.xml` 的 `frac_itemtop` 依次是
−0.0431 / 0.1228 / **+0.3599** / +0.7446，最后一条已越出面板）。

> ⚠️ **一个测量口径的坑（对后来者）**：任务书建议的
> `(lineCenter − panelTop) / panelHeight` **不是稳定量** —— 当前行折行成两行时它会变。
> 同一自动位置下实测 `frac_center` = **0.4720（一行）/ 0.5490（两行）**，
> 而「当前行 item top」口径恒为 **0.3599**。
> 上滑那一轮 `frac_center = 0.3540` 看起来「差不多就是 0.36」，会被误判成「没有 bug」；
> 同一次实测的 `frac_itemtop = 0.1649` 才暴露出 141px 的真实位移。
> **口径**：`frac_itemtop = (节点文本 top − 40px item 内边距 − 面板 top) / 面板高`。

**「当前行」的认定用了两个互相独立的信号，结果始终一致**：

1. 面板根节点的无障碍 `liveRegion` 文本；
2. **像素判据**：当前行是屏幕上唯一用主题主色 `#8B5CF6 = (139,92,246)` 绘制的文本
   （实测 99.9% 墨迹像素为紫色，最亮像素恰为 `(139,92,246)`）。

像素判据是**必需的**：实测歌曲里 `We are electric` 同屏出现 3 次，纯文本匹配会挑中错误的那一次。

## 2. 当前定位代码（只读审计）

`app/src/main/java/com/takahashirinta/ncrust/ui/player/NcrustLyricsPanel.kt`：

| 位置 | 内容 | 触发条件 |
|---|---|---|
| `LaunchedEffect(lines)` | `scrollToItem`（无动画） | **换歌词表 / 换歌** |
| `LaunchedEffect(isVisible)` | `scrollToItem`（无动画） | 面板显现 |
| `LaunchedEffect(forcedScrollTrigger)` | `scrollToItem`（无动画） | 外部强制（播放器展开） |
| `LaunchedEffect(currentIndex)` | `animateScrollToItem`（**有动画**） | **跨行**，且 `!userScrolling` |
| `LaunchedEffect(isScrollInProgress)` | 只改 `userScrolling` / `lastAutoScrolledIndex` | 用户滚动开始 / 结束 |

**唯一的「跟随」路径是第 4 条，而它的开头就是**
`if (userScrolling || currentIndex == lastAutoScrolledIndex) return@LaunchedEffect`。

第 5 条在用户滚动结束后 `delay(5000)`，然后**只做两件不滚动的事**：

```kotlin
} else if (!listState.isScrollInProgress && userScrolling) {
    delay(5000)
    userScrolling = false          // 放下「别跟着我」的旗子
    lastAutoScrolledIndex = -1     // 允许下一次跨行重新跟随
}
```

⇒ **5 秒超时不解救当前位置**；只有「超时之后恰好发生了一次换行」才会回正。

## 3. 复现：「手动调整后留在原地」（决定性实验）

暂停态（**没有任何换行可能**，且已用静止性对照证明屏幕是静态的），
当前行全程为同一句 `めき煌めきと君も`：

| 时刻 | 节点 bounds | `frac_itemtop` | 相对自动位置 |
|---|---|---|---|
| 滑动前（自动位置） | `[1206,470][2480,617]` | **0.3599** | 0 |
| 滑动后 **+1.64 s** | `[1206,838][2480,985]` | **0.7565** | **+367.9px = +39.65% 面板高** |
| 静置 **+8.57 s** | `[1206,838][2480,985]` | **0.7565** | **不变** |
| 静置 **+20.61 s** | `[1206,838][2480,985]` | **0.7565** | **不变** |

**+8.57s 与 +20.61s 两张 PNG 的 md5 完全相同** ⇒ 不是「缓慢回正」、也不是「动画没跑完」，
而是**逐字节没有任何变化**。

**另两条独立复现**：

- 下滑（另一首歌）：`0.3599 → 0.7543 → 0.7543（+37.3s）→ 0.7543（+51.9s，md5 相同）`
- **上滑（反方向）**：`0.3599 → 0.1649 → 0.1649（+10.6s）`

**播放态的对照**（严格计时 +1.80 / +8.62 / +20.68 s）：

- +8.62s 时面板内**完全没有紫色墨迹** ⇒ 当前行整行在可视区之外；
- +20.68s 时回到 `0.3599`。

应用自己的日志给出了权威时刻：`16:56:58.082 NcrustLyricNotify: re-post on lyric line change:
We are electric` = 滑动后 **+6.8 s** —— 刚刚越过 5s 超时，于是那次**换行**把它拉了回去。
⇒ **播放态下换行不断发生，bug 被掩盖；暂停 / 间奏 / 长句时永久暴露。**

### 3.1 仪器可信度（这一段是为了让上面的数字可信）

- **静止性对照**：暂停态连拍 3 张、间隔 1.5s、不触碰 —— 三张 md5 **完全相同**，
  `compare -metric AE` 均为 **0px**。这也证明暂停时逐字光标不会自行推进，
  所以暂停态确实是「只可能由 idle 逻辑引起变化」的干净环境。
- **灵敏度对照**：`05b`(自动) vs `06p`(滑动后) = **79347.7px** 差异；
  `20-paused3-baseline` vs `PAUSED3-A` = **61031px** 差异。
  即这套方法看得见真实的位移，上面的「0 差异」不是因为方法迟钝。

## 4. 播放 / 暂停 / seek 会不会重置那个 5 秒计时器？（任务书 7.2 要求探针确认）

**结论：都不会。唯一的回正触发是「歌词换行」。**

| 试验 | 观察 | 结论 |
|---|---|---|
| 暂停 → 滑走 → **按播放** | +2.0s 仍 `0.4170`（未回正）；+5.6s **换行** → `0.3599` | 播放**不**重置计时器、**不**触发回正 |
| 暂停 → 滑走 → **点歌词行 seek** | seek 确实生效（0:45 → 0:40），此后 **24 秒 7 次采样全部 `0.4041`** | seek **不**回正 |
| 对照：从位移状态按播放 | +1.9s 仍 `0.4041`；+5.4s **换行** → 精确 `0.3599` | 回正与换行**严格同刻**，与操作无关 |

### 这条结论如何影响本版的设计

任务书 7.2 把「播放/暂停/seek 是否重置计时」留给探针决定。探针给出的答案是
**它们对现有实现没有任何影响**，而本版的设计据此**刻意收窄**交互判据：

- **seek 有它自己两条重定位路径**（点行 → `onLineClick` 立即定位；拖进度条 → 行变化触发跟随），
  再让 seek 重置计时只会**推迟**回正，没有任何额外收益；
- **播放/暂停根本不移动列表**，把它算作「交互」会让「暂停后翻看歌词」这个
  **最需要回正**的场景永远等不到回正（用户不会每隔 5 秒按一次暂停）。

⇒ 本版把判据收窄成一句：**只有手指落在面板上才算交互**（这正是任务书 7.2 的字面语义）。

## 5. 本版的修法（探针结论 → 设计）

| 问题 | 修法 | 落点 |
|---|---|---|
| 5s 超时只放旗子、不滚动 | 超时到点**真的滚回目标位置**（`animateScrollToItem`，动画平滑） | `NcrustLyricsPanel.kt` 的世代计时器 |
| 「只有换行才回正」导致暂停/间奏永久不回正 | 计时器绑在**用户交互世代**上，与换行解耦 | `LyricsAutoCenter`（纯逻辑 + 单测） |
| 拖拽中被拽走 | 到点那一刻检查 `pointerDown`，**还在按就放弃**；松手时世代 +1 重新计时 | `LyricsAutoCenter.shouldRecenter` |
| 横屏 3 行视口下 36% 视觉偏上 | 横屏目标比例改成 **0.5（视口正中）** | `LyricsPanelScroll.CENTER_FRACTION` |
| 「什么时候算交互」含糊 | **只认触摸**（探针 §4 的依据） | `NcrustLyricsPanel` 的 `PointerEventPass.Initial` 观察器 |
| 计时器可能无限重排（铁律 8） | 一个世代只 `delay` 一次、只判定一次；世代号回绕到 **1** 而不是 0 | `LyricsAutoCenter.nextGeneration` |

## 6. 未验证 / 边界（如实）

1. **只在横屏大屏模式下做了「滑走 + 静置」的对照**；竖屏只验证了自动位置
   （`frac = 0.3591` ≈ 0.36），**没有**做竖屏的滑走静置试验。
   所以「该现象是否只在横屏出现」本轮**没有**数据支撑 —— 从代码看它与方向无关
   （同一份 `NcrustLyricsPanel`），但这是推理，不是实测。
2. **本轮的静置间隔不全是精确 8 秒**：三条暂停试验的实际间隔是 37.3 / 51.9 / 10.6 秒
   （都 > 5 秒所以有效，但不是 8 秒）。**精确计时的是 `PAUSED3`（+1.64/+8.57/+20.61s）
   与 `PLAYING`（+1.80/+8.62/+20.68s）两组。**
3. 第一次播放态试验只等了 2.4 秒（< 5 秒超时，不足以验证），已作废并隔离到
   `probe-raw/invalid-timing/`，随后用精确计时重做。那两张作废的 PNG 已被正确计时的
   同名文件覆盖，不再单独存在（README 内已写明）。
4. 暂停试验里 A→B 有约 0.3% 的像素差，但**所有节点 bounds 完全一致**、且 B==C 逐字节相同 ——
   是手势结束后约 2 秒内的一次**亚像素级渲染沉降**。**成因未确证，本轮不做推断。**
5. 有一轮试验落到纯音乐曲目（面板只有一行、不可滚动），**无信息量**，已记录不采用。
6. 本 ROM 的 `dumpsys window` **没有 `mRotation` 这个键**（只有 `mCurrentFocus`）。
   横屏由三条互相独立的证据确认：`dumpsys display` 的
   `mOverrideDisplayInfo … app 2560 x 1440, rotation 1`、`screencap` 实际输出 2560×1440、
   以及应用自身日志 `16:47:45.002 NcrustBigScreen: big screen: manual enter, holding landscape`。
7. 横屏目标从 0.36 改到 0.5 是**有意的行为改变**（任务书 7.2 用了「居中」这个词），
   **不是**修一个算错的数 —— 探针证明 0.36 的自动定位本身精确。本版的真机验证需要
   重新测量横屏自动位置是否落到 0.5（见 `EVIDENCE.md`）。
